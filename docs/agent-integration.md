# Agent access (MCP)

Veles exposes a permission-controlled [MCP](https://modelcontextprotocol.io) server at `/api/mcp` so an agent (e.g. Hermes on a VPS) can read and change allowed parts of the key owner's data without database access.

- Transport: stateless Streamable HTTP via `@modelcontextprotocol/server` (`createMcpHandler`); 2025 and 2026 protocol clients both work.
- Auth: Better Auth API keys (`@better-auth/api-key`). Keys are hashed at rest, do not expire, are rate-limited to 120 requests/minute, and are checked on every request. Revoking a key cuts the agent off right away.
- Code: `apps/web/src/pages/agent/` (start at `mcp.api.ts`).
- All tools with their inputs: [agent-tools.md](./agent-tools.md), generated by `pnpm mcp:tools`.

## Setup

1. In Veles, open **Account → Agent access** and choose which features AI may read or write. Every switch starts off, including for existing keys.
2. Create a key and copy it. It is shown only once.
3. Configure the agent's MCP client:

```yaml
mcp_servers:
  veles:
    url: https://<veles-host>/api/mcp
    headers:
      Authorization: Bearer vls_...
```

Smoke test from the VPS:

```sh
curl -s https://<veles-host>/api/mcp \
  -H "Authorization: Bearer $VELES_KEY" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
```

## Tools

| Tool           | Input                                                  | Returns                                       |
| -------------- | ------------------------------------------------------ | --------------------------------------------- |
| `get_access`   | none                                                   | current read and write consent                |
| `list_records` | `resource`, `cursor?`, `limit?` (≤100), `from?`, `to?` | `{ items, nextCursor }`; repeat until `null`  |
| `get_record`   | `resource`, `id`                                       | the record, or `null` if missing or not yours |

Read resources. Related rows are nested, so agents never match children to parents by id. Photos and images are public URLs that agents can download.

| Resource            | Feature consent | One record                                                                            |
| ------------------- | --------------- | ------------------------------------------------------------------------------------- |
| `notes`             | Notes           | Note with `content`, or shopping list with its `items`                                |
| `weights`           | Weight          | `date`, `weightKg`, `photoUrls`                                                       |
| `recipes`           | Recipes         | Recipe with `total` and `perPortion` nutrition, `imageUrls`                           |
| `food_days`         | Food diary      | One logged day (`id` = `date`): `entries`, `total`, and the `goal` in effect that day |
| `calorie_goals`     | Nutrition goals | Goal by `effectiveDate`                                                               |
| `food_products`     | Food catalog    | Shared product with `per100g` nutrition, `imageUrl`                                   |
| `workout_sessions`  | Workouts        | Session with its routine, exercises, and sets                                         |
| `workout_routines`  | Workouts        | Routine with its exercises and planned set types                                      |
| `workout_exercises` | Workouts        | Exercise with `lastDoneOn` and `sessionCount`                                         |

Lists are newest first. `weights`, `food_days`, `calorie_goals`, and `workout_sessions` accept inclusive `from`/`to` dates (`YYYY-MM-DD`). Nutrition is `{ kcal, macros: { protein, fat, carbs } }` in kcal and grams. `food_days.goal` is `null` unless Nutrition goals read consent is on. Diary entries are not available: they are end-to-end encrypted in the browser.

Read tools appear only when at least one feature permits reads. The `list_records` tool description lists permitted resources and their units. Each call also checks current consent.

## Consent and writes

Write consent needs read consent: granting write also grants read, and revoking read also revokes write. Consent applies to all keys owned by the account and is checked at each tool call. Turning off a switch cuts off that operation for existing keys. Refresh `tools/list` after a change to discover the available tools.

Every feature has write tools. Each feature's tools appear only while its Write switch is on:

**Notes and shopping lists**

- `create_note`: `title`, `content`, `type` (`note` or `shopping_list`). New notes are private. Use empty content for shopping lists, then add list items.
- `update_note`: `id`, optional `title` and `content`.
- `delete_note`: `id`; also deletes its list items.
- `set_note_shared`: `id`, `shared`; shares or unshares an owned note with connected friends.
- `toggle_note_type`: `id`; converts note content to list items or list items back to text.
- `create_list_item`: `noteId`, `name`.
- `update_list_item`: `id`, `name`.
- `set_list_item_checked`: `id`, `checked`.
- `delete_list_item`: `id`.

**Weight**

- `save_weight`: `date`, `weightKg`; replaces the weight for that date. Photos stay.

**Recipes**

- `create_recipe`: `name`, optional `description`, `ingredients`, `tags`, `portions`, `rating`, `kcal`, `protein`, `fats`, `carbs` (whole recipe, whole numbers).
- `update_recipe`: `id` and only the fields to change. Images stay.
- `rate_recipe`: `id`, `rating` (1–5).

**Food diary**

- `log_food`: `productId` (from `food_products`), `grams`, `date`. Nutrition is copied from the product.
- `log_custom_food`: `name`, `kcal`, `date`, optional `grams`, `protein`, `fat`, `carbs`.
- `update_food_log`: `id` and all fields. Entries with a `productId` keep their name and scale nutrition by grams.
- `delete_food_logs`, `move_food_logs` (`date`), `copy_food_logs` (`date`): `ids` (up to 200).
- `multiply_food_logs`: `ids`, `factor` (up to 20).

**Nutrition goals**

- `set_calorie_goal`: `date`, `kcal`, optional `protein`, `fat`, `carbs`. The goal applies from `date` until the next goal.

**Food catalog** (shared by all accounts)

- `lookup_food_barcode`: `barcode`; imports a missing product from Open Food Facts.
- `create_food_product`: `name`, `kcalPer100g`, optional `barcode`, `productSizeGrams`, `proteinPer100g`, `fatPer100g`, `carbsPer100g`.
- `update_food_product`: `id`, all fields, and `today` (the user's local date). Entries of that product logged on `today` by any account are recalculated.

**Workouts**

- Sessions: `start_workout` (`date`), `start_routine` (`routineId`, `date`), `update_workout` (`id`, `name?`, `finished?`), `delete_workout`. Only one session can be open.
- Session exercises: `add_workout_exercise` (`workoutId`, `exerciseId` or `newExercise`), `update_workout_exercise` (`notes`), `move_workout_exercise` (`up`/`down`), `remove_workout_exercise`.
- Sets: `add_workout_set` (`sessionExerciseId`), `duplicate_workout_set`, `update_workout_set` (`type`, `weightKg`, `reps`, `durationSeconds`, `distanceKm`, `done`), `delete_workout_set`.
- Exercises and routines: `update_exercise`, `save_routine_from_workout`, `update_routine_from_workout`, `update_routine`, `delete_routine`.

Creates return `{ id }` or the saved record; other writes return `{ success: true }`. Permission denials and operation failures are MCP tool errors (`isError: true`). Write tools call the same validators and server operations as the app. MCP can change only data that the key owner owns, plus the shared food catalog. It cannot change a friend's shared note. Ownership, IDs, and timestamps are set by the server. Keys cannot act as browser sessions or change account consent.

Agents cannot upload or replace photos. Weight photos, recipe images, food log photos, and product images stay as they are, and are managed in the app. The app has no delete for weights, recipes, goals, products, or exercises, so MCP has none either.

## Adding a feature

1. Define its label in `apps/web/src/lib/agentAccess.ts`.
2. Add a reader in `mcp-read-*.server.ts` that filters by the owner and nests related rows, then register it in `mcp-resources.server.ts` with its feature and a description of units.
3. Add write tools in `mcp-write-*.server.ts` that reuse the feature's validators and server operations. Run every data tool through `runAgentTool` (writes via `agentWriter`) and keep MCP writes scoped to the key owner.
4. Register the write tools in `mcp-server.server.ts` behind the feature's write permission. Keep all permissions off by default.
5. Run `pnpm mcp:tools` and commit the updated `docs/agent-tools.md`.

## Database rollout

Before merging, a human must run `pnpm db:generate -- --name=agent_access`, review and commit the generated migration for both `apikey` and `user_agent_permission`, and apply it to dev and prod. Do this before merging to `main`, which deploys the app. This PR does not run Drizzle commands or verify against a migrated database.
